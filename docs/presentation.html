A Figma library an AI can read.

A suite of skills for Claude Code that cleans up the components of a Figma design system, so that an agent (a coding assistant, a screen generator) understands them without guessing.

What it's for

An agent reads your library the way it's built: its names, its properties, its layers, its descriptions. When a property is called Property 1, when a label sits in Frame 12, when nothing says what a component is for, the agent guesses. Ariane removes the guessing:

  • names that say what things do, in English, the same from one run to the next: layers, properties, the component's name;
  • a structure without empty shells: frames that do nothing are removed, after proving that the rendering doesn't move by a single pixel;
  • reliable descriptions: what the component is for, what it contains, where it lives, what it shouldn't be confused with.

An illustrative example. Untangling what Property 1 mixes together is the job of the corrected copy, which Ariane builds next to the original for you to review.

How it works

  1. The check reads a component (or a board, or several links) and gives a verdict: "well built" or "needs rework". It lists at most five issues, each ready to paste into a ticket, at most three questions for the design system team, and a plan to fix it. It writes nothing in Figma.
  2. The proposal, if you ask for it: a copy corrected according to the plan, placed above the original. The original and its instances don't move.
  3. Naming, in a fixed order: layers first, then properties and the component's name, then descriptions. Each step only starts if the previous one is entirely clean, with no open question.
  4. Validation, once you've reviewed the copy: it takes the proper name and the original's place; the old one moves to a "waiting for migration" page, removed from publishing, with all its instances intact.
  5. Replacing in screens, later and only if you ask: instances of the old component move to the new one, in batches, after a survey and a dry run.

On a screen (a mockup with no main component), Ariane only handles layers: there are no properties or descriptions to write.

What the check gives you

A verdict per component, then each issue written as a ticket for the design system team: what's wrong, why it gets in the way, what to do, and where. Here is one, translated: Ariane writes its tickets in French.

buttonNeeds rework · 2 issues

The label and the icon can't be set from the panel

Priority
High
What's wrong
button has no text property and no instance swap. Most placed buttons change their label by hand, in the layers.
Why it matters
The label can't be found in the panel, and a typed label is lost as soon as type changes.
To do
Plan, step 3. May affect placed instances: check on a branch.
Where
button, all variants

All of it goes into a dated page in tickets/, in the folder where you run Claude Code: one ticket per component, a button to copy each one, a filter by verdict. It stays after the session closes.

The plan that follows says what to create, merge or link, step by step, and which public design systems do it that way. Ariane never judges completeness: a missing state isn't a defect. It judges what is built.

What you need

Claude Code
Preferably with an Opus model: Ariane was tuned on Opus.
Figma connector
The official one (Figma's MCP server), with write access enabled. Ariane always goes through it.
A paid Figma seat
A Full or Dev seat on Professional, Organization or Enterprise, and a file that belongs to that plan. Figma limits connector calls: 20 a month on Starter, View or Collab, 200 a day with a Full or Dev seat, 600 on Enterprise (Figma's limits). 20 a month isn't enough for a single component.
git
To get Ariane and its updates. And a Figma components file you can edit.

Install

git clone https://github.com/MCQX7/ariane-skills.git
cd ariane-skills
claude

The skills live in .claude/skills/: they're active as soon as you open Claude Code in this folder. That's the simplest way to work: one folder per design system, which keeps its own lexicon and memory.

To have them in all your projects, add one link per folder, from the root of the repository:

mkdir -p ~/.claude/skills
for s in .claude/skills/*/; do
  ln -sfn "$PWD/${s%/}" ~/.claude/skills/"$(basename "$s")"
done

The link to ariane-referentiels/ is essential: each skill looks for its reference files next to itself, and stops if it can't find them. Ariane fetches its latest version itself (git pull) at the start of each run.

Before your first run

Work in a Figma branch

On a published library, renaming a component or a property reaches every file that uses it when you publish, and restoring an older version no longer changes that. A branch also gives you a readable comparison of everything Ariane did.

Ariane can't create branches: it asks you to confirm the safety net is in place.

Put each component in a board

A corrected copy is checked board against board: the original and its copy, each in its own frame or section. A component alone on the page can be checked and renamed, but its copy can't go through its full verification.

Write permissions

Ariane writes its description log, and the lexicon or the project frame when you approve a line, under .claude/. Claude Code asks for your approval there, and a session with nobody at the keyboard (claude -p) can't write there at all.

Tell Ariane about your product

Three files in ariane-referentiels/ belong to your project. They ship empty and Ariane works without them; when you move to another design system, they're emptied again.

FileWhat it holdsWho writes it
cadre-mission.mdWhat the Figma file doesn't say: your design system's constraints, your product's rules, your answers to the check's usage questions.You; Ariane suggests lines, written only if you approve them.
lexique-mission.mdYour domain's vocabulary: business words and their translation, product names, options specific to your project.Ariane suggests, you approve.
journal-descriptions.mdThe memory of approved descriptions, to find neighbouring components from one session to the next.Ariane only, after your GO.

The first one helps most: a few lines on what your product imposes save the check from asking questions you already know the answer to.

A first run

Open Claude Code in Ariane's folder, copy the link of a component (or a board) in Figma, and just talk. The entry point is /ariane-orchestrator, but a Figma request is enough.

  1. Check. "Check this component: <link>". You get the verdict, the issues, the questions and the plan. If there's a usage question, Ariane asks you and completes the plan with your answer.
  2. Choose what's next. Build the proposal (only if the verdict is "needs rework"), rename directly on the component, or stop here.
  3. Answer the questions. When a name really can't be decided, Ariane marks it ❓ and asks you. Descriptions are shown to you first: nothing is written without your GO.
  4. Review the copy in Figma, next to the original. Give feedback in plain words; it's applied to that copy.
  5. Validate. "The copy is approved: <link>". The copy takes over, the old one goes to "waiting for migration".
  6. Later, migrate the screens, if you ask. Ariane never suggests it on its own.

You can also check several components at once, or clean up a whole screen.

Language, time and cost

Ariane is written in French: its verdicts, tickets and descriptions are in French. The names it sets are in English, following fixed conventions: camelCase, show/is/has for booleans, function rather than appearance. It works best on a design system whose source names are in French or English.

It reads a lot before writing, on purpose: a stable name and an accurate description require knowing the whole component. Expect one long session per component handled end to end (check, copy, naming): around half an hour, and from a few dollars to about fifteen on Opus depending on the component's size. A check on its own is much shorter. Run a single component first to measure it on your side.

What Ariane doesn't do

  • It never deletes the old component: it's renamed, set aside and removed from publishing; its instances stay in place until migration.
  • It doesn't create branches, versions or publish in Figma: you publish.
  • It doesn't touch other files: only the one you give the link to.
  • It doesn't replace anything in screens unless you explicitly ask.
  • It doesn't fill the lexicon on its own: every new word waits for your approval.
